# 产品定位

## 目标

nailong-bot 是类似 Grokbot、运行在用户自己电脑上的个人 agent，让用户用更少的注意力获得更多有效产出。
用户用自然语言交代目标和必要边界，Bot 结合获准的本地资源、外部模型与服务推进工作，保存进度，
在有可用成果、重要变化或需要用户决定时主动联系用户。

优先减少监督进度、重复解释、筛选信息、协调步骤和返工的负担。
这里描述产品目标；当前实现与限制见 [design](design.md)，交付状态见[开发计划](dev/plans/README.md)。

## 核心场景

- **一次性委托：** 用户交代任务，Bot 自行处理常规步骤、核对结果，交付可使用的成果。
- **持续性委托：** 用户交代关注对象和目的，Bot 持续观察、筛选变化、分析并在授权范围内推进后续工作。

例如：“帮我盯着 OpenBot 的更新，关注对我们这个 fork 有用的改动，结合本地代码做影响分析，值得处理时告诉我。”
用户无需反复提醒检查，也无需每次重新解释关注原因。

## 产品原则

- **低成本启动：** 自然语言是主要入口，结合已有上下文采用合理默认值，只澄清影响目标、结果或授权的关键缺口。
- **授权内自主推进：** 自行选择方法和处理常规步骤；已有授权延续有效，超出授权或需要关键取舍时再请求用户参与。
- **保持连续性：** 保存委托、进度、结果和待处理事项；支持补充与中断后的继续，避免重复产生外部副作用。
- **交付有效成果：** 结果可使用或支持下一步决定；完成有依据，部分完成、失败和不确定性明确表达。
- **珍惜注意力：** 围绕成果、重要变化和阻碍反馈，无关变化和正常等待不持续制造通知。
- **用户可控制：** 能查询进度、补充要求、调整范围、暂停或停止委托。

## 第一版范围

主要运行在用户自己的电脑上，使用获准的本地项目、文件和工具，允许连接外部模型与服务。
用户离开电脑后可以通过 Telegram 等消息渠道联系 Bot，前提是电脑和服务在线。
休眠、关机或服务停止期间可能暂停；恢复后应保留进度，按任务要求继续或补查。
本地运行不代表数据只在本机处理，外部依赖和数据流需明确说明。

优先打通“自然语言启动 → 执行或持续观察 → 判断与推进 → 有依据的成果 → 调整与停止”。
暂不优先打磨服务器/NAS 部署、多人团队协作、大量渠道覆盖或复杂工作流编辑器。
上游已有能力可保留，新增投入服务于核心委托体验。

## 取舍与衡量

评估功能时说明减少哪类注意力投入，增加什么可用成果，以及用户如何掌握状态和边界。
关注追问、催办、重复解释、不必要确认和通知是否减少，工作是否可靠、返工是否降低。
持续委托应在无需反复提醒时产生价值。调用数或消息数不能单独代表产出；成本和耗时结合结果评估。

## 待明确

首批 source 与优先任务、默认检查频率和补查方式、通知门槛，以及不同行动的授权方式与默认边界。
